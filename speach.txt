Хорошая идея — рынок инструментов автоматизации для Instagram (ManyChat, ChatPlace, SMMplanner и подобные) вполне жив, и технически это реализуемо через официальный Instagram Graph API (не через скрапинг — скрапинг Instagram банит аккаунты и юридически рискован, забудьте про этот путь сразу).

Как это устроено технически
Instagram (для Business/Creator аккаунтов, привязанных к Facebook-странице) даёт через Meta Graph API:

Webhooks на комментарии — подписка на поле comments для медиа/страницы. Когда кто-то оставляет комментарий, Meta шлёт POST-запрос на ваш сервер в реальном времени.
Private Reply API — специальный эндпоинт, который позволяет отправить пользователю приватное сообщение в директ в ответ на его комментарий (это именно тот механизм, который использует ChatPlace/ManyChat). Есть нюансы:
Работает только в течение ограниченного окна после комментария (порядка 7 дней),
Это отдельный тип отправки, не обычная переписка,
Если хотите вести полноценный диалог дальше — попадаете под правило 24-часового окна для messaging (либо human agent tag, либо message tags).
Для доступа к этим правам нужно пройти App Review в Meta (permissions: instagram_manage_comments, instagram_manage_messages, pages_manage_metadata и т.д.) + бизнес-верификацию приложения. Это не про код, а про бюрократию — обычно 1-4 недели, иногда дольше, могут запросить видео-демо использования.
На каком языке писать бэкенд
Раз вы React 19 + TypeScript — берите Node.js/TypeScript для бэкенда. Причины:

Единый язык и типы во всём стеке (можно шарить DTO/типы между фронтом и бэком через monorepo).
Webhook-приёмники — это по сути I/O-bound задача (принять запрос, положить в очередь, ответить 200 OK быстро), и Node асинхронная модель для этого отлично подходит.
Экосистема богатая: express/fastify/NestJS, bullmq для очередей, prisma/drizzle для БД.
Python (FastAPI) тоже был бы неплохим выбором объективно, но раз вы не пишете на нём продуктивно — не вижу смысла усложнять себе жизнь ради безразличной разницы в возможностях.

Архитектура (примерно)
Instagram/Meta Webhook → HTTPS endpoint (Node/Express)
        → верификация подписи (X-Hub-Signature)
        → запись события в очередь (Redis + BullMQ)
        → воркер: matching по keyword'ам из БД
        → если совпало → вызов Private Reply API
        → лог отправки в Postgres (для аналитики/анти-дублей)
Плюс отдельно:

OAuth-флоу для подключения IG-аккаунтов пользователей (Meta Login for Business),
хранение и рефреш long-lived токенов (~60 дней),
rate-limit handling (у Meta есть лимиты на кол-во вызовов API).
План по этапам (как вы и предлагали)
Этап 1 — скрипт отслеживания комментариев

Зарегистрировать Meta App, тестовый IG Business аккаунт, Facebook Page.
Поднять простой Express-сервер с публичным HTTPS (ngrok на старте).
Настроить webhook subscription на comments.
Логировать входящие комментарии в консоль/файл, реализовать keyword-matching.
Реализовать вызов Private Reply API вручную (без очередей пока).
Этап 2 — API

Вынести конфигурацию ключевых слов/сообщений в БД (Postgres + Prisma).
CRUD для "сценариев" (keyword → сообщение).
Очередь (BullMQ/Redis) вместо синхронной обработки, чтобы не терять события при пиках.
Авторизация пользователей, мультиаккаунтность (один пользователь — несколько подключённых IG).
Логи отправленных сообщений, защита от повторной отправки одному человеку.
Этап 3 — фронтенд

Дашборд: список подключённых IG-аккаунтов, конструктор сценариев, статистика отправок, история комментариев.

Сложность реализации
Сам код — средней сложности, ничего экстраординарного для вас как разработчика. Основные риски не в коде:

App Review / верификация бизнеса — самая долгая и непредсказуемая часть, закладывайте время.
Ограничения Private Reply (окно в 7 дней, нельзя просто слать что угодно кому угодно) — нужно проектировать логику с оглядкой на это.
Rate limits и стабильность вебхуков — нужна ретрай-логика, идемпотентность обработки событий.
Политики Meta по спаму — если сообщения будут восприниматься как спам, аккаунт могут ограничить, это стоит учитывать в UX (частота, персонализация).

Хорошая новость: если это только для вашего личного аккаунта — полный App Review можно пропустить.

Почему
У Meta есть два уровня доступа:

Standard Access — работает только для аккаунтов, у которых есть роль в вашем приложении (admin/developer/tester). Вы вручную добавляете свой аккаунт в эту роль в Meta App Dashboard, и всё работает без всякого ревью, бессрочно.
Advanced Access — нужен только если приложением будут пользоваться чужие аккаунты (клиенты, которых вы не добавляли вручную). Вот это уже требует App Review, бизнес-верификацию и т.д. — но вам это не нужно.
Так как ваш IG-аккаунт остаётся под вашим же Meta-приложением как аккаунт с ролью — вы просто регистрируете приложение, добавляете себя как admin/tester, и сразу получаете полный доступ к нужным разрешениям (instagram_manage_comments, instagram_manage_messages и т.п.) без ревью.

Что всё же обязательно, даже для себя
Instagram аккаунт должен быть Business или Creator (не личный) — переключается за минуту в настройках приложения, бесплатно.
Аккаунт должен быть привязан к Facebook-странице — это требование архитектуры Graph API, тоже 5 минут.
Приложение должно оставаться в Development mode — не переключайте в Live, это как раз и запускает требование ревью. В dev-режиме всё работает для аккаунтов с ролью.
Webhook endpoint всё равно должен быть на HTTPS с валидным сертификатом (Meta не примет http или self-signed) — на старте достаточно ngrok/Cloudflare Tunnel, для постоянной работы — любой VPS с Let's Encrypt.
Что это меняет в плане
Практически ничего в архитектуре — просто убираем самый долгий и непредсказуемый этап (2-4 недели ожидания + риск отказа с первого раза). Можно сразу переходить к:

Регистрация Meta App → добавление себя как tester/admin.
Перевод своего IG в Business/Creator + привязка к Facebook Page.
Настройка webhook (ngrok на старте) → скрипт-приёмник комментариев.
Дальше — как и планировали: matching по ключевым словам → Private Reply API.
Единственный нюанс на будущее: если вы вдруг решите открыть это друзьям или превратить в продукт для других людей — тогда придётся либо добавлять их вручную как testers (до ~25 человек это разрешено без ревью в некоторых конфигурациях, но лимит стоит проверить в актуальной документации на момент реализации), либо всё же проходить Advanced Access.
